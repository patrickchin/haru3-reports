## 1. Code style is lenient. Readability > rules.

- **No hard cap on file or function length.** A 600-line file that reads
  top-to-bottom and tells one coherent story is better than five
  150-line files that hide that story behind imports.
- **Split files when splitting helps the reader**, not because a rule
  says so. The v1 `ReportEditForm.tsx` (705 LOC) was bad because the
  parts were *unrelated*, not because the number was big.
- Same for functions. A clear 80-line function beats four 20-line
  functions whose only purpose is to hit a guideline. Use judgement.
- The standard-path-first rule (`crypto.randomUUID`, `Blob`/`fetch`,
  blessed primitives) **still applies** — that's about avoiding
  vendor-replacement bugs, not about line counts.

**What to remove from earlier docs.** Any "max X lines" / "extract once
above N lines" rule in [03-implementation.md](03-implementation.md)
§3 is advisory only. Treat as smell flags, not gates.

## 2. Data lives close to where it's used.

- A screen that needs report-notes calls the React Query hook **inside
  that screen**, not three levels up to be drilled down as a prop.
- Hooks colocate with their consumers when they have one consumer.
  Promote to a shared `hooks/` only when a second consumer appears.
- Same for derived state, formatters, and tiny helpers — keep them in
  the file that uses them until somebody else needs them.

## 3. Reusable components, sparing props.

- A reusable component takes **what it renders**, not a sprawl of
  callbacks for every conceivable variation. If a `<Card>` grows past
  ~6 props, it's probably two components in a trench coat.
- **Children > callbacks.** Pass JSX into slots before passing render
  callbacks. Pass a `<TrailingAction>` child before passing `onAction`,
  `actionLabel`, `actionVariant`, `actionDisabled`, ….
- **Composition > configuration.** `<Sheet><Sheet.Title/><Sheet.Body/><Sheet.Actions/></Sheet>`
  beats `<Sheet title=… body=… actions=[{label,variant,onPress,disabled},…] />`
  for anything non-trivial.
- **Too many props is a code smell.** ≥7 props, or ≥3 callbacks, or any
  `*Variant` + `*Mode` + `*Kind` triplet → reach for composition.

## 4. Don't drill flags as callbacks. The `USE_FIXTURES` lesson.

- v1's `summarize-voice-note` passed `updateFileMetadataFn`,
  `transcribeFn`, etc. as injected callbacks so fixture mode could
  swap them. The result was a tangled signature, a real bug
  (`updateFileMetadataFn: async () => {}` no-op), and code that nobody
  could read top-to-bottom. See [01-lessons-learned.md](01-lessons-learned.md)
  bug entry for 2026-05-08.
- **v2 rule:** an inline `if (USE_FIXTURES) { … }` branch right next to
  the real call is the preferred shape. It is grep-able, single-file,
  and impossible to leave half-stubbed.
- Same rule for any other "swap behaviour by mode" need: prefer an
  inline branch with a clear flag over a callback-injection seam.
  Reach for dependency injection only when there are ≥3 production
  implementations, never just to support a test.
- Tests that need a different behaviour mock the **leaf** primitive
  (the network call, the storage write), not the surrounding orchestration.
  This is the same rule as [/Users/patchin/.claude/rules/common/standard-path-first.md](../../../../.claude/rules/common/standard-path-first.md):
  don't mock the I/O primitive being changed — mock around it.

## 5. TypeScript is a tool, not a religion.

- **Strict mode on, but pragmatic.** A `Record<string, unknown>` at a
  boundary is fine. Inferring types from runtime data with
  `ReturnType<typeof fn>` is fine. `// @ts-expect-error: <reason>` with
  a one-line reason is fine when the alternative is 40 lines of
  conditional generics.
- **Reuse types. Stop re-declaring.** If the database row is the
  source of truth, derive everything from one `Report` type
  (e.g. via `Database['public']['Tables']['site_reports']['Row']`
  from generated supabase types). Don't redeclare it in every hook,
  component, and helper.
- **Discriminated unions for state machines, plain interfaces for
  data, and that's it.** No advanced conditional-type acrobatics
  unless they earn their seat.
- **Avoid type sprawl.** A `types/` folder is allowed to be small and
  shared. If a type is used in one file, it lives in that file.

## 6. Server sync: keep it boring.

The recurring sync bugs (R3, R4, R6, R11, voice-note auto-summary
invisible) all came from clever optimistic updates, multi-tab sources
of truth, or assumed-stale caches. v2 does the **simplest thing that
shows correct data**, even if it's slightly slower:

- **Single source of truth: the server.** All data is fetched via
  React Query. Local state mirrors React Query, never the other way
  around.
- **Read pattern.** `useQuery` with sensible `staleTime`
  (5–30 s for lists, 0 for things being actively edited). On screen
  focus → `refetchOnWindowFocus` (RN equivalent: `useFocusEffect` →
  `query.refetch()`). On app foreground → invalidate everything
  user-bound. That's the whole policy.
- **Write pattern.** Mutate → `await` server response → invalidate.
  **No optimistic updates by default.** Add them only for the two
  flows where v1 proved they matter (upload-queue pending rows,
  voice-note summary), and only with a unit test that exercises the
  in-flight state transition (R11).
- **Conflicts.** If user A edits a report while user B is offline,
  last-write-wins on the server, and B's next refetch shows A's
  version. We do not attempt offline write reconciliation. If the
  user has unsaved local edits when a refetch arrives, **the local
  edit wins in the UI until the user explicitly discards or saves**
  (we do not silently overwrite a draft). This is the entire
  conflict story for v2 launch.
- **Realtime.** Out of scope for v2 launch. If we want it later,
  Supabase Realtime → invalidate the matching React Query key. No
  custom diff merging.
- **Offline writes.** Out of scope. Mutations require connectivity
  and surface a clear error. Upload queue is the exception (it has
  always been an offline-tolerant subsystem) and keeps its design.
- **Cross-device sync.** Implicit, via the refetch policy above. No
  push channel, no version vectors, no CRDT. We are pre-release; we
  optimise for "I can reason about this in 30 seconds" over "no one
  ever sees a 2-second-stale screen".

## 7. We are pre-release. We can break things.

- **No users in production.** The "phased migration" framing in
  [05-migration-plan.md](05-migration-plan.md) is overkill.
- The actual plan: **rewrite in `apps/mobile-v2/`, delete `apps/mobile/`
  when v2 is at parity, rename `apps/mobile-v2/` → `apps/mobile/`.**
  No legacy preservation, no OTA-rollback rehearsal, no internal-test
  cohort, no `apps/mobile-legacy/` parking lot. Deleted is deleted.
- **No backwards compatibility.** If the v2 schema needs a column
  rename or a destructive migration, do it. There is nothing to
  protect.
- **Phases are still useful as ordering**, not as gates. We don't
  hold v3-of-something behind a v2 release window. Each phase ships
  to `dev` directly.
- **CI must stay green on `dev`.** That is the only hard rule from
  the migration plan that survives.

## 8. What stays from the original docs

- The R-pattern lessons in [01-lessons-learned.md](01-lessons-learned.md).
  Those are bug forensics, not style opinions, and they cost real
  hours to learn.
- The upload-queue and audio-playback architectural sketches in
  [02-architecture.md](02-architecture.md) §5–§6. v1 got those right.
- The standard-path-first banned-patterns list. That rule is about
  avoiding vendor-replacement bugs, not about being strict.
- The RLS test rule from [AGENTS.md](../../../AGENTS.md). It is the
  one test rule that has caught actual security bugs.
- The typed `testIds` registry idea. Maestro coupling is real and
  the registry costs ~15 LOC.

## 9. Quick reference card

| If you're tempted to… | Do this instead |
|---|---|
| Split a file because it crossed N lines | Leave it. Split when the parts are unrelated. |
| Add a 5th callback prop to a component | Use children/slots. Or fork into two components. |
| Inject a function so tests can swap it | Inline `if (USE_FIXTURES)` or mock the leaf primitive. |
| Add a new `interface ReportRow` somewhere | Reuse the supabase-generated row type. |
| Write an optimistic update "for snappiness" | Don't. Wait for server. Add it later if a user notices. |
| Merge offline edits with server changes | Don't. Last write wins; surface a conflict toast if it matters. |
| Plan a staged rollout | Ship to `dev`. We have no users. |
| Preserve `apps/mobile/` "just in case" | `git rm -rf` it. The history is in git. |
